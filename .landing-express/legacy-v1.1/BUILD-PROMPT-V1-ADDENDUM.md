# Build Prompt Contract — V1 Addendum

This addendum extends the existing v0 Build Prompt Contract. Preserve all v0 sections and add the following when relevant:

- EXECUTION CONTEXT: GREENFIELD / EVOLUTION / VISUAL REFACTOR / REBUILD.
- VISUAL SYSTEM DIRECTION with explicit styling behavior.
- VISUAL CONTEXT PROFILE derived from the approved editorial/color system.
- MOTION HIERARCHY: PRIMARY / SUPPORTING / AMBIENT.
- ASSET DELIVERY CONTRACTS with required modality/provider/fallback policy.
- VISUAL INTEGRATION CONTRACTS for context-aware asset compositing/integration.
- CAPABILITY REQUIREMENTS with no-silent-fallback policy.
- MODEL / EFFORT RECOMMENDATION **for the next material action**, including action, complexity, recommended configuration and reason.
- EXECUTION ECONOMY DECISIONS for material model/capability/asset routes where total-cost trade-offs matter.
- PRESERVATION REQUIREMENTS for existing/refined implementations.
- GLOBAL EXPERIENCE BASELINE requirements applicable to navigation, interaction states, affordance, safe viewport, responsive safety, legibility and minimum feedback.
- SEMANTIC HIERARCHY MAP for material elements/recurring controls using the V1.1 semantic classes.
- SECTION ENRICHMENT MAP for material sections, recording narrative/functional importance, expression status, enrichment decision and rationale.
- COMPLEXITY / CREATIVITY BUDGET for material or experimental sections, recording primary focus, creative density, supporting mechanisms, competition risks and BALANCED / UNDER-COMPOSED / OVER-COMPOSED status.
- TRANSITION MAP for important section boundaries, recording CONTINUITY / CONTRAST / RESET intent, narrative bridge, visual/color/depth behavior and motion/interaction handoff.
- MOTION CAPABILITY MAP for material motion units, distinguishing STATIC / UI_MOTION / PROGRAMMATIC_MOTION / GENERATED_MOTION, plus hierarchy, engine/provider, control source, fallback and relevant cost/reuse/control rationale.

Operational contracts such as Session Pause/Resume and Runtime Lifecycle remain framework-level policies and do not need verbose duplication inside every Build Prompt. The executor must still obey them.

V1 binding rules:

1. Required modality is binding; video/frame-sequence cannot silently become a static substitute.
2. Required capability is binding; when fallback is `block`, missing tool stops execution.
3. Visual Integration derives from Visual Context Profile, not a hard-coded dark treatment.
4. Every generated asset keeps the v0 generation budget discipline plus objective retry conditions.
5. Approved existing structure marked PRESERVE must not regress during localized refine/regenerate.
6. V1.1 Global Experience Baseline is binding independently of visual style.
7. Semantic role must survive styling: primary actions/navigation cannot be demoted into metadata/decorative treatment.
8. Section enrichment is contextual. `NONE` is a valid approved decision and media must never be added by quota.
9. Every governed section must preserve a recognizable primary focus. `CONCEPT: STRONG / EXECUTION: OVER-COMPOSED` should trigger reduction of competing layers before concept replacement.
10. Section boundaries must honor their approved transition intent. Strong contrast is valid when intentional; unrelated stacked-template behavior is not.
11. Motion hierarchy and motion modality are separate contracts. PRIMARY/SUPPORTING/AMBIENT defines perceptual importance; STATIC/UI_MOTION/PROGRAMMATIC_MOTION/GENERATED_MOTION defines execution mode.
12. Generated motion is not the default. Code-native motion may be preferred when it satisfies the approved experience with appropriate control/reuse/cost.
13. Approved motion modality is binding; generated and programmatic motion must not silently substitute one another when the experience materially changes.
14. Model/effort must be recalculated for the current material action. A previous phase's HIGH recommendation is not inherited automatically by a localized refine.
15. Material under- or over-reasoning requires explicit surface/user handling according to `MODEL-GATE.md`.
16. Economy optimizes total reasonable cost while preserving the quality floor; it must not force an underpowered model or a lower-quality capability.
17. Generated assets require an approved destination, role and budget before execution.
18. Dev/start/server/watch/preview processes are forbidden by default unless explicitly authorized; authorized persistent processes must follow START -> USE -> STOP -> VERIFY TERMINATED.
19. Heavy build validation such as `npm run build` requires explicit request or approval of a validation step that clearly needs it.
20. Material phase changes and blocks must persist a resume checkpoint according to `SESSION-LIFECYCLE.md`.
