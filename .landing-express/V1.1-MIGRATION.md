# Landing Express — V1.1 → V1.2 Migration Map

This document defines which V1.1 concepts remain valuable, where they live in V1.2, and which legacy contracts are no longer part of the core runtime.

## 1. Migration principle

V1.2 preserves **useful product knowledge**, not V1.1 workflow complexity.

The normal V1.2 path is:

```text
le-start → copilot → PROMPT READY → le-refine | le-end
```

Legacy artifacts may remain readable as evidence/compatibility, but they must not create new mandatory phases or restore automatic implementation ownership.

## 2. Concepts retained

| V1.1 concept | V1.2 destination |
| --- | --- |
| Session persistence | `SESSION-LIFECYCLE.md` + `conception-state.json` + prompt/refine/completion metadata |
| Semantic / visual hierarchy | `EDITORIAL-INTERPRETER.md` + `VISUAL-INTERPRETER.md` + `EXPERIENCE-QUALITY.md` |
| Section enrichment | `EXPERIENCE-QUALITY.md` + `SECTIONS` / `CINEMATIC_OPPORTUNITIES` |
| Creativity / complexity budget | `EXPERIENCE-QUALITY.md` + existing visual/section state |
| Transition quality | `EXPERIENCE-QUALITY.md` + `NARRATIVE` / `SECTIONS` / `MOTION` |
| Programmatic motion routing | `EXPERIENCE-QUALITY.md` + `GENERATED-MEDIA-POLICY.md` + `MOTION` / `THREE_D` |
| Model / effort governance | `MODEL-GATE.md` + `REASONING-ADAPTER.md` |
| Economy | `EXPERIENCE-QUALITY.md` + `GENERATED-MEDIA-POLICY.md` + Reasoning Adapter |
| Review findings | evidence that may selectively reopen current Conception State; never automatic execution instructions |
| Responsive / safe viewport baseline | `EXPERIENCE-QUALITY.md` + compiled prompt acceptance criteria |

## 3. Legacy contracts retired from the V1.2 core

The following filenames may remain in the source repository or in migrated installations for historical compatibility, but they are not required by the promoted V1.2 core:

```text
DIRECTION-V1-ADDENDUM.md
BUILD-PROMPT-V1-ADDENDUM.md
BUILD-ORCHESTRATOR.md
CALIBRATION-V1.1.md
EXECUTION-ECONOMY.md
RUNTIME-LIFECYCLE.md
REVIEW-GAP-CLASSIFICATION.md
```

Fresh V1.2 Project Packs should not need these files to run the promoted lifecycle.

When updating an existing Project Pack, preserve old copies as legacy evidence rather than using them as active core contracts.

## 4. Build Orchestrator retirement

`Build Orchestrator` is not a V1.2 core phase.

The legacy `le-build` command may remain callable during the migration window, but it is only a compatibility handoff for the current compiled prompt.

It must not:

- mutate implementation files;
- generate assets;
- run dev/build/preview/deploy;
- invoke an implementation agent automatically;
- become a required step between `PROMPT READY` and completion.

## 5. Review migration

`le-review` is not required to finish V1.2 conception.

Useful review findings can be consumed as evidence:

```text
review evidence
→ compare with current intention/state
→ reopen only affected decisions when still relevant
→ Refine if needed
```

Do not preserve review-state machinery merely because a V1.1 session contains it.

## 6. Legacy session reading

V1.2 must remain able to recover useful context from older sessions when possible.

Legacy values such as:

```text
READY FOR BUILD
BUILD
REVIEW
START NEXT ITERATION
AWAITING_CYCLE_DECISION
build-prompt.md
compiled-prompt.md
```

are historical evidence, not current lifecycle commands.

Normalize them to the current interaction model when presenting the session to the user. Do not require the user to understand or continue the legacy phase.

## 7. No automatic entry / implementation

Any legacy SessionStart/UserPromptSubmit hook that automatically starts Landing Express must be removed during install/update when it is identifiable as a Landing Express hook.

Opening a repository or AI surface must not start conception or execution. `le-start` remains explicit.

## 8. Compatibility boundary

Compatibility is successful when:

- old sessions remain readable enough to recover current intention/approved material state;
- old commands can fail safely or route to the new behavior;
- no old contract is required for a fresh V1.2 interaction;
- legacy state never overrides the current user's intention;
- the user does not need to learn V1.1 terminology to continue.

## 9. Removal policy

A legacy contract/command may be removed completely in a later version when:

1. no promoted V1.2 flow depends on it;
2. Project Pack update has a safe migration path;
3. representative legacy sessions remain recoverable;
4. documentation identifies the replacement;
5. removal does not silently discard user-authored historical evidence.
